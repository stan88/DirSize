# 第 4 階段設計：背景服務與 named pipe

狀態：第 8 節的決定事項都已確認（2026-11-05），8.4、8.5 依實測結果決定。

## 1. 目標與範圍

- 一個 Windows 服務在背景維護各磁碟的索引（第 2、3 階段的 `NtfsLiveVolume`），開機時從快取載入，之後持續追日誌。
- 前端以一般權限透過 named pipe 查詢，日常使用不需要系統管理員權限，也不跳 UAC。
- **輕量**：平常幾乎不耗資源；需要整顆重掃時，不搶前景程式的資源，也不會因為服務本身卡住而把 CPU 吃滿。
- **安全**：服務看得到所有資料夾，回答查詢前，必須確認呼叫者本人有權限看那個資料夾。
- 本階段**不做**：圖形前端（第 5 階段）、安裝程式與多語系（第 6 階段）。服務的安裝與移除先用 CLI 指令。

## 2. 實測依據（前幾個階段）

| 項目 | 數字 |
|---|---|
| 平常追日誌（每 5 秒一次） | 單一核心的 0.02%～0.05% |
| 整顆建索引 | 4～6 s，約佔滿一個核心，大多是核心模式；開機後立刻做要 8～20 s |
| 建索引時記憶體峰值 | 約索引大小的 2 倍（C: 索引 50～64 MB，峰值約 130 MB） |
| 開機時載入快取＋補上關機期間的變動 | C: 0.8 s，D: 0.4 s |
| 存一次快取 | C: 42 MB、0.3～0.4 s |

結論：成本集中在**整顆重掃**。服務的設計重點是讓重掃少發生，發生時不搶資源。

## 3. 服務本身

- **帳戶：LocalSystem**。
  - 要打開磁碟區 handle 讀 `FSCTL_QUERY_FILE_LAYOUT` 和 USN 日誌，前幾個階段實測需要提權。LocalService 的權限清單裡沒有 SeBackupPrivilege。
  - 用 `SERVICE_REQUIRED_PRIVILEGES_INFO` 只保留需要的權限。文件寫明，指定之後，SCM 會在啟動時從 token 移除其他權限。
  - **不需要 SeBackupPrivilege**：實測停用時，建索引和讀日誌的結果和啟用時相同（DEVLOG「實測程式 service_probe」）。
  - 清單只有 SeChangeNotifyPrivilege。文件寫明，這個權限永遠不會被移除。前端用識別等級連線（8.5），文件寫明，識別等級的冒充不需要 SeImpersonatePrivilege。實作後要以服務身分實測確認；如果實測發現還需要其他權限，再加進清單，並記錄原因。
  - **服務 SID**：用 `SERVICE_SID_TYPE_UNRESTRICTED`，token 裡會加上服務自己的 SID。不用 RESTRICTED，因為它會讓 token 變成寫入受限，快取資料夾的權限設定和檢查都得跟著改。
- **啟動：自動（延遲開始）**。文件寫的是「其他自動啟動的服務啟動後，再加一小段延遲」，沒有保證確切時間。好處是不和開機搶資源。
- **生命週期**：
  - 主執行緒要儘快呼叫 `StartServiceCtrlDispatcherW`，文件寫的是 30 秒內。
  - 控制處理函式要立刻返回，也是 30 秒內，所以只負責設定旗標、通知工作執行緒。
  - 啟動時回報 `SERVICE_START_PENDING`，並依 `dwCheckPoint`／`dwWaitHint` 回報進度。
  - **停止與關機**：
    - 接受 `SERVICE_CONTROL_PRESHUTDOWN`，在這時存快取，符合已決定的存檔時機。
    - 文件寫明，一般的 SHUTDOWN 通知預設只有約 20 秒可以收尾。
- **失敗時自動重啟**：設定 `SERVICE_FAILURE_ACTIONS`：第 1、2 次失敗後 1 分鐘重啟，第 3 次起不再重啟，24 小時後重新計算次數。另外開啟 `fFailureActionsOnNonCrashFailures`，讓「以錯誤碼停止」也算失敗。
- **主控台模式**：同一個執行檔可以用主控台模式執行，方便測試，不必經過 SCM。文件寫明，不是由 SCM 啟動時，`StartServiceCtrlDispatcherW` 會回傳 `ERROR_FAILED_SERVICE_CONTROLLER_CONNECT`。
- **安裝與移除**：CLI 指令 `dirsize-service install|uninstall`，需要系統管理員權限。第 6 階段改由安裝程式處理。

## 4. 執行緒與資源

- **索引執行緒**：每顆磁碟一個，擁有自己的 `NtfsLiveVolume`。追日誌和回答查詢都在這個執行緒上做，所以索引不需要上鎖。查詢很便宜，只是查表。
- **管道執行緒**：用 overlapped I/O 處理所有連線，把請求交給對應的索引執行緒，等它回覆。
- **重掃**：在另一個執行緒上建一份新的索引，完成後交給索引執行緒換上。重掃期間繼續用舊索引回答，並標示「更新中」，這是第 3 階段已決定的。
- **降低優先順序**：
  - 只有重掃執行緒使用 `THREAD_MODE_BACKGROUND_BEGIN`。文件寫明，這會降低它的資源排程優先順序，讓前景活動幾乎不受影響。文件也提醒，背景模式的執行緒要避免和其他執行緒共用鎖、heap 等資源，否則會發生優先順序反轉。所以重掃執行緒只建自己的資料，最後一次交出。
  - 文件說「和使用者互動的行程不應該用」process 層級的背景模式，所以回答查詢的執行緒保持一般優先順序。
  - 整個行程開啟 EcoQoS（`ProcessPowerThrottling`），以及較低的記憶體優先順序（`ProcessMemoryPriority`）。文件說 EcoQoS 適合「不影響前景體驗的工作」，可以延長電池、減少發熱和風扇噪音。
- **CPU 上限（8.4 決定：整個服務最多 1 個核心）**：
  - 服務啟動時建立 Job Object，把自己放進去，設定 `JOB_OBJECT_CPU_RATE_CONTROL_HARD_CAP`。實測確認行程可以把自己放進 job。
  - 實測確認上限是以**整台電腦**計算，所以 `CpuRate = 10000 ÷ 邏輯處理器數`，最少為 1，也就是 1 個核心的量。
  - 這是安全網：即使程式出錯開了很多執行緒，也最多只用 1 個核心。實測 1 個核心的上限下，重掃約 6.5 s，同時間其他執行緒的延遲最多 0.4 ms。
  - 不設得比 1 個核心更低：實測上限真的卡住時，同一個行程的所有執行緒都會一起停，回答查詢最多會延遲 0.3～0.5 s。
- **追日誌的間隔**：每 5 秒一次，實測成本是單一核心的 0.02%～0.05%。
- **記憶體**：每顆磁碟一份索引，重掃期間暫時有兩份。狀態查詢會回報實際用量。

## 5. 重掃

- **一定要重掃的情況**（第 3 階段）：
  - 日誌接不上：ID 變了，或記錄被修剪；
  - 索引不一致；
  - 一次變動超過 5 萬個；
  - 快取不能用。
- **定期校正（見 8.3）**：建索引之前就開著、之後一直寫的檔案，日誌裡沒有它們的記錄，索引會慢慢偏離實際大小。實測 5 分鐘累積的誤差不到 2 MB。
- **閒置偵測**：服務跑在 session 0，`GetLastInputInfo` 只回報呼叫者自己的 session，所以不能用。可以用的有：
  - `RegisterPowerSettingNotification` 搭配 `DEVICE_NOTIFY_SERVICE_HANDLE`，通知會送到服務的控制處理函式。
  - `GUID_GLOBAL_USER_PRESENCE`：任何 session 的使用者狀態改變，包括 `PowerUserInactive`，也就是超過使用者活動逾時都沒有操作。文件寫明，服務應該註冊這一個。
  - `GUID_ACDC_POWER_SOURCE`：電源是交流電還是電池。
  - `GetSystemTimes`：用來算整台電腦的 CPU 忙碌程度。

## 6. Named pipe

- **名稱**：`\\.\pipe\DirSize`。
- **建立**：
  - `FILE_FLAG_FIRST_PIPE_INSTANCE`：防止別的程式先佔用這個名稱。文件寫明，帶這個旗標時，如果名稱已經被建立過，會回傳 `ERROR_ACCESS_DENIED`。服務遇到這個錯誤要大聲報錯並停止，不能改用別的名稱。
  - `PIPE_REJECT_REMOTE_CLIENTS`：拒絕遠端連線。
  - 訊息模式（`PIPE_TYPE_MESSAGE | PIPE_READMODE_MESSAGE`），overlapped I/O。
  - 同時連線數設上限，例如 16 個。
- **管道的權限**：預設權限會讓 Everyone 和匿名帳戶都能讀，所以不用預設值，改用 SDDL：SYSTEM 和 Administrators 完整權限，Authenticated Users 只能讀寫，不能建立新的管道實例。
- **前端要確認連到的是真的服務**：寫入任何資料之前，先比對 `GetNamedPipeServerProcessId` 和 SCM 回報的服務 PID，不一致就中斷連線。前端用識別等級連線，見 6.1。
- **協定**：
  - 每則訊息是「版本、類型、長度、內容」；
  - 請求最大 64 KB，因為路徑最長 32,767 個 UTF-16 字元，約 64 KB；
  - 回應依子資料夾數量分頁；
  - 每個連線 5 秒內沒送完一個請求，就中斷；
  - 格式不符就中斷該連線，不影響其他連線。
- **請求類型**：
  - `Status`：每顆磁碟的狀態（就緒、更新中、無索引），以及記憶體用量、最後一次追日誌的時間；
  - `QueryFolder(path)`：該資料夾的合計，以及第一層子資料夾的名稱和合計。

### 6.1 怎麼確認呼叫者有權限看那個資料夾

基本做法：**用呼叫者的身分打開那個路徑**。打開成功，就表示呼叫者有權限列出這個資料夾。再從打開的 handle 取得檔案 ID，用 ID 在索引裡找到對應的資料夾。

這樣存取檢查完全交給 NTFS 判斷，和使用者自己在檔案總管裡打開的結果一樣，包括上層的「周遊」檢查。

- **一定要「失敗就拒絕」**：文件寫明，`ImpersonateNamedPipeClient` 失敗時，之後的動作會用服務自己的身分執行，而服務是 SYSTEM，什麼都打得開。所以：
  - 冒充失敗，就直接回錯誤，不碰檔案；
  - 冒充之後，用 `OpenThreadToken` 確認 token 的冒充等級至少是 `SecurityImpersonation`；
  - 不論成功或出錯，都用 scope guard 保證 `RevertToSelf`。
- **路徑**：
  - 只接受本機的磁碟機代號路徑，拒絕 UNC、`\\?\GLOBALROOT` 和裝置路徑；
  - 打開之後，確認 handle 所在的磁碟區（GUID 和序號）是有索引的那一顆，才用檔案 ID 查索引；
  - 其他情況一律不從索引回答。
- **冒充等級（8.5 決定：識別等級）**：
  1. 前端連線時用 `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`。就算管道名稱被別的程式搶先佔用，對方也拿不到可以冒充前端使用者去開檔的權限。
  2. 服務讀到一則請求後，呼叫 `ImpersonateNamedPipeClient`，用 `OpenThreadToken(OpenAsSelf = TRUE)` 取得呼叫者的 token，再立刻 `RevertToSelf`（scope guard）。token 的等級必須是 Identification 或 Impersonation，Anonymous 一律拒絕；任何一步失敗也都拒絕。
  3. 服務**以自己的身分**驗證路徑、打開資料夾，取得磁碟區、檔案 ID 和安全描述元（擁有者、群組、DACL）。
  4. 用呼叫者的 token 呼叫 `AccessCheck`，要求 `FILE_LIST_DIRECTORY`。允許才從索引回答，拒絕就回「沒有權限」。
  5. 子資料夾是否「沒有權限」，也用同樣的方式逐一判斷，每頁最多判斷一頁的子資料夾數。

  實測（一般權限）：識別等級的 token 可以用在 `AccessCheck`，允許和拒絕都判斷正確；在識別等級下開檔會直接失敗（錯誤 1346），不會退回用服務自己的身分開。

  和「用呼叫者身分直接開檔」的差異：只檢查目標資料夾本身的權限，不檢查上層資料夾。服務以 SYSTEM 執行時讀不到某個資料夾的安全描述元，就回「沒有權限」，也就是失敗就拒絕。

## 7. 回應的內容與隱私（見 8.1）

服務回答 `QueryFolder(F)` 時，呼叫者已經證明可以列出 F，所以 F 底下第一層的名稱本來就看得到。問題在**大小**：F 的合計包含呼叫者打不開的子資料夾。例如一般使用者查 `C:\Users`，會看到其他使用者設定檔的大小。

## 8. 決定事項（2026-11-05，都採用 A）

### 8.1 呼叫者看得到哪些大小（決定：A）

- **A（建議）**：呼叫者能列出 F，就回傳 F 的合計，以及每個子資料夾的合計，包括呼叫者打不開的子資料夾。前端在打不開的子資料夾旁標示「沒有權限」。
  - 優點：簡單、快，數字和磁碟實際用量一致。
  - 缺點：看得到其他使用者資料夾的大小，看不到裡面的名稱。
- **B**：同 A，但打不開的子資料夾不顯示大小，只顯示「沒有權限」。
  - 缺點：用 F 的合計減去其他子資料夾，還是算得出來。要完全隱藏，F 的合計也得扣掉，就變成 C。
- **C**：每個使用者看到的合計，只包含自己有權限的部分，和檔案總管「內容」的算法一樣。
  - 缺點：每次查詢都要對子樹裡的每個資料夾做存取檢查，C: 有數十萬個資料夾，會很慢，也需要按使用者分開快取。

### 8.2 要為哪些磁碟建索引（決定：A）

- **A（建議）**：所有本機固定式 NTFS 磁碟，自動處理。外接式磁碟和非 NTFS 的磁碟不建索引，前端改用逐目錄掃描。
- **B**：由使用者選擇。

### 8.3 定期校正（決定：A）

- **A（建議）**：只在必要時重掃（第 5 節）。另外，每次重掃後，把「重掃前後大小不同」的檔案加進開啟中檔案的追蹤清單。這些多半是一直開著寫的檔案，加進去之後就會持續重查，誤差不會再累積。
- **B**：A，再加上每天一次的整顆重掃，只在使用者閒置（`GUID_GLOBAL_USER_PRESENCE`）而且接著交流電時做。
- **C**：都不做，只在必要時重掃。

### 8.4 CPU 上限（決定：A）

- **A**：整個服務上限 1 個核心，當作安全網。重掃另外用背景優先順序。
- B：整個服務上限半個核心。重掃約 12 s，重掃期間查詢偶爾延遲約 0.3 s。
- C：重掃交給另一個子程式，對子程式設更低的上限，建完存成快取檔，再由服務載入。比較複雜。

### 8.5 前端連線的冒充等級（決定：A）

- **A**：識別等級，服務用 `AccessCheck` 判斷，詳見 6.1。
- B：冒充等級，服務用呼叫者的身分直接開檔。判斷和檔案總管完全一致，但萬一管道名稱被搶先佔用，前端會把可以冒充自己的權限交給對方。

## 9. 實作順序與驗證

1. **實測程式**（`tools/service_probe.cpp`，不出貨，提權執行）——2026-11-05 完成，結果見 DEVLOG：
   - 在 job 裡以不同的 CPU 上限建索引，量經過時間，同時確認查詢的反應時間；
   - 確認建索引和讀日誌是否需要 SeBackupPrivilege；
   - 確認識別等級的 token 能不能用在 `AccessCheck`，以及用識別等級冒充時開檔的結果。
2. **pipe 協定與存取檢查**：先寫成和服務無關的元件，用單元測試涵蓋格式錯誤、超過大小、逾時、路徑種類。
3. **服務本體**：生命週期、主控台模式、install/uninstall 指令。
4. **實機驗證**：
   - 一般權限的 CLI 透過 pipe 查詢，結果要和 `cache load` 的比對一致；
   - **負面測試**：一般權限查詢 `C:\ProgramData\DirSize`（只有 SYSTEM 和 Administrators 能存取），以及其他使用者的設定檔，都必須被拒絕；
   - 重開機後服務自動啟動、從快取載入；關機時存快取；
   - 長時間執行時量 CPU 和記憶體。
