# 第 3 階段設計：USN 增量更新與快取

狀態：已確認（2026-11-05）。第 8 節的三個問題由使用者決定，都採用 A。依據 `docs/DEVLOG.md` 的實測結果。

## 1. 目標與範圍

- 索引存成快取檔，下次啟動直接載入，再用 USN 日誌補上中間的變動，不必整顆重掃。
- 索引載入後持續讀日誌，讓資料夾大小保持最新。
- 做成核心元件，第 4 階段的服務直接使用；本階段用 CLI 指令測試。
- 本階段**不做**：背景服務、named pipe（第 4 階段）、前端、ReFS。

## 2. 實測依據（摘要）

- 讀日誌要提權，並用 `GENERIC_READ` 開 `\\.\X:`。一般權限是錯誤 1，所以沒有服務時的逐目錄掃描無法增量更新。
- 日誌上限是 32 MB（另加 8 MB 調整量）。實測當下 C: 保留了 10.3 小時的歷史，D: 24.1 小時。讀完整個日誌不到 0.1 秒。
- 寫入量：C: 的 `NextUsn` 從 11-03 的 verify 到 11-05 的實測，約 34.6 小時增加 272 MB，平均每小時約 7.9 MB；D: 約 59 MB，每小時約 1.7 MB。
- USN 記錄的檔案 ID 和索引是同一套編號，含序號。
- `FSCTL_QUERY_FILE_LAYOUT` 的 FILEID 篩選：
  - 只比對 MFT 記錄號、不比對序號，範圍包含結尾，刪除的 ID 回傳 0 筆。
  - 1 萬個 ID 約 0.4 秒，比逐檔開啟快 3～10 倍。
  - 一次給 10 萬個 ID 要 20 秒以上，不是線性。整顆重掃 C: 約 9 秒。

## 3. 更新原則：重新查詢，不從記錄推算

USN 記錄沒有大小，順序也不保證，所以**不從記錄計算差額**。做法：

1. 從上次套用到的 USN 讀到日誌結尾，收集**變動過的檔案 ID 集合**，不管變動原因是什麼。
2. 用 FILEID 篩選重新查這些 ID 的目前狀態。查回的資料和第 2 階段一樣，有名稱、上層資料夾、大小、屬性，可以沿用同一個解析器。送出的方式：
   - 篩選只比對 MFT 記錄號（低 48 位元），所以送出前**去掉序號**。
   - 依記錄號去除重複、排序，連續的記錄號合併成一個範圍。這樣範圍不會重疊；文件規定範圍不能重疊。
   - 每批最多 1 萬個範圍。
3. 回傳的項目依記錄號對回要查的 ID，再比對**完整 ID**（含序號）。記錄號被新檔案重用時，舊 ID 視為已刪除，新 ID 視為新增。實測 C: 一次查 10 萬個 ID，有 40 個就是這種情況。
4. 每個 ID：先扣掉它在索引裡的舊貢獻（每個計入的資料夾及其上層），再加上新狀態的貢獻。查不到就是刪除。

這個做法結果和處理順序無關，重複套用也沒關係。所以第 2 階段建索引期間發生的變動，從掃描前記下的 USN 重新套用一次即可。

讀日誌時設 `ReturnOnlyOnClose = 0`。只看關閉記錄的話，開著的檔案（記錄檔、`-wal`）會一直落後，就是第 2 階段在逐目錄掃描看到的問題。

變動的 ID 太多時（初定 5 萬個），直接整顆重掃比較快。實作時要量：分批和合併範圍之後，查詢時間是否變回線性，再決定這個門檻。

## 4. 資料夾的變動

- **新增、刪除**：跟檔案一樣處理。資料夾被刪除時索引裡如果還有子項目，把它們的貢獻全部扣掉。正常情況下子項目會先被刪除。
- **改名、搬移**：上層資料夾不同時，整個子樹的合計從舊的各層上層扣掉，加到新的各層上層。
- **變成看不到**：資料夾變成 junction、符號連結等 reparse point，或搬進隱藏資料夾（例如 `$Extend`）時，整個子樹從合計移出。
- **變成看得到**：例如從隱藏資料夾搬出來，或 reparse point 被移除。第 2 階段建索引時，看不到的子樹整個不保留，只記在排除統計裡；這時變動集合裡只有這個資料夾本身的 ID，重新查詢拿不到裡面的內容。這種情況很少見，所以**直接整顆重掃**。
- **根目錄**：變動的項目上層是根目錄時，重新列舉根目錄（約 20 項），套用第 2 階段「根目錄列舉看得到才計入」的規則。

增量更新不維護排除統計（中繼檔案、隱藏資料夾、命名串流等）、`rootListingMatched`、跟隨的 reparse 種類和診斷樣本：看不到的子樹不在索引裡，無法更新。這些數字只代表上次整顆掃描。

第 2 階段的 `Finish()` 是整顆磁碟一次算完。要把可見性判斷和計入規則拆成獨立函式，給全量建立和增量更新共用，避免兩邊規則不一致。

## 5. 索引的修改方式

目前的檔案表、資料夾表都依 ID 排序，可以二分搜尋，但插入和刪除要搬移整個陣列。

- **新增**：放到另一個「新增區」陣列，再用雜湊表從 ID 查位置。只有新增的項目進雜湊表，所以記憶體只隨變動量增加。
- **刪除**：標記為已刪除，不搬移陣列。
- **整理**：存快取前，或新增區超過一定比例時，把新增區合併回排序好的主表，再移除已刪除的項目。
- **硬連結**：檔案的額外連結在 `extraLinks`。只有 `countedLinks > 1` 的檔案需要找，直接線性掃描。C: 約 7 萬筆，每次只要幾十微秒。
- **查詢**：依 ID 找檔案或資料夾的函式，都要同時查主表（二分搜尋）和新增區（雜湊表）。第 2 階段 `verify` 裡的查詢函式只查主表，要一起改。
- 記憶體：C: 的索引表格約 50 MB。新增區和雜湊表大約是「變動項目數 × 50 bytes」，10 萬個變動約 5 MB。

## 6. 快取檔

- **位置**：`%ProgramData%\DirSize\cache\`，每顆磁碟一個檔案，檔名用磁碟區 GUID，不用磁碟機代號。
- **存取權限**：資料夾只有 SYSTEM 和 Administrators 能讀。快取裡有整顆磁碟的資料夾名稱，包括其他使用者的資料夾，一般使用者不能直接讀。這是第 4 階段安全要求在快取端的部分。
- **內容**：
  - 檔頭：格式版本、計算規則版本、磁碟區 GUID 和序號、日誌 ID、**已套用到的 USN**、各表格的筆數、檢查碼。
  - 檔頭之後是整理過的各表格原始內容。
- **已套用到的 USN**：存的是索引實際更新到的位置，不是存檔當下日誌的 `NextUsn`。否則中間的變動會被漏掉。
- **寫入**：先寫到同一資料夾的暫存檔並清到磁碟，再用 `MoveFileExW`（`MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`）取代舊檔。寫到一半斷電時，舊檔還在。`ReplaceFileW` 的文件沒有說取代是原子操作，失敗時檔名可能停在中間狀態，所以不用。
- **檢查碼**：CRC-32，自己實作。只用來發現檔案損壞，不是安全用途。
- **何時存檔**：結束時；有變動時也定期存，例如每 10 分鐘。
- 大小：C: 約 50 MB，不壓縮。

## 7. 什麼時候快取不能用（整顆重掃）

- 檔案不存在、讀取失敗、檢查碼不符、格式版本或計算規則版本不同。
- 磁碟區 GUID 或序號不同。
- 日誌 ID 不同：日誌被重建，或被 NTFS 換了新 ID。
- 已套用到的 USN 小於 `FirstUsn` 或 `LowestValidUsn`：中間的記錄已經被修剪掉。
- 讀日誌失敗：`ERROR_JOURNAL_ENTRY_DELETED`（1181）、`ERROR_JOURNAL_DELETE_IN_PROGRESS`（1178）、`ERROR_JOURNAL_NOT_ACTIVE`（1179），或其他錯誤。
- 有資料夾從看不到變成看得到（見第 4 節）。
- FILEID 篩選不能用（舊版 Windows），見 8.1。

## 8. 決定事項（2026-11-05，都採用 A）

### 8.1 最低 Windows 版本

**決定：A。**

FILEID 篩選從 Windows 10 1809 起才有，目前專案目標是「Windows 10 以上」。

- **A（建議）**：最低版本改成 Windows 10 1809。微軟的生命週期頁面寫著 Windows 10 家用版／專業版 1809 的支援到 2020-11-11，Windows 10 整體在 2025-10-14 結束支援。程式偵測到篩選不能用時，只做整顆重掃，不做增量更新。
  - 這也要改 `CLAUDE.md` 和 README（中英文兩個版本）裡的目標系統。
- **B**：維持 Windows 10 全版本，舊版改用逐檔開啟（`OpenFileById`＋`FileStandardInfo`）。這樣比篩選慢 3～10 倍；而且硬連結和名稱要另外用 `FindFirstFileNameW` 查，等於多一套更新程式要寫、要測。

### 8.2 日誌接不上的情況

**決定：A。**

日誌只在**有新記錄寫入**、超過上限時，才從最舊的記錄開始修剪（文件：在檢查點修剪到 `MaximumSize + AllocationDelta`）。所以能保留多久，取決於寫入量，不是經過的時間。以 C: 平均每小時 7.9 MB、上限約 40 MB 計算，約等於 5 小時的連續使用量。

依文件推論（還沒實測），關機期間沒有寫入，不會用掉日誌，所以「關機一晚」本身不會讓快取失效。第 4 階段的服務會一直讀日誌，只有下面幾種情況會接不上：
- 服務停止期間，電腦仍在使用、寫入量超過約 40 MB。
- 開機後到服務啟動前的寫入量太大。
- 在其他系統下修改過這顆磁碟，例如雙系統，或把硬碟接到別台電腦。

要確認的話，可以在關機前和開機後各跑一次 `usn-probe`，看 `FirstUsn` 有沒有變。

- **A（建議）**：不改系統設定。接不上就整顆重掃，C: 約 9 秒，在背景執行。照上面的分析，有服務在跑時很少發生。
- **B**：由程式加大日誌。`FSCTL_CREATE_USN_JOURNAL` 可以直接修改現有日誌的 `MaximumSize`，不必刪除。但這會改到整台電腦的系統設定，也會影響其他使用日誌的軟體。

### 8.3 重掃期間要不要先顯示舊資料

**決定：A。**

快取接不上、正在整顆重掃時：

- **A（建議）**：先載入舊快取顯示，標示「更新中」；重掃完成後再換成新索引。打開就有數字，只是可能不是最新的。
- **B**：不顯示舊資料，等重掃完成。

這會影響核心 API 的設計（索引要有「最新／更新中」狀態），所以在本階段決定。

## 9. 驗證

- **單元測試**（不需提權）：用合成的版面資料和變動 ID，測新增、刪除、改名、搬移、硬連結、可見性改變、根目錄規則、記錄號重用。另外確認「全量建立」和「先建立再增量套用」的結果完全相同。
- **快取**：存檔後再載入，結果要完全相同；也測截斷、改壞位元組、版本不符的情況。
- **實機驗證**：新增 CLI 指令，載入快取或建立索引，等一段時間後套用日誌，再和一次全新的整顆掃描逐資料夾比對。除了比對當下正在寫入的檔案，結果應該完全一致。
