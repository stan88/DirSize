# 第 2 階段設計：NTFS 快速掃描與資料夾索引

狀態：已確認（2026-11-03）。第 7 節的計算規則由使用者決定。依據 `docs/DEVLOG.md` 的實測結果。

## 1. 目標與範圍

- 用 `FSCTL_QUERY_FILE_LAYOUT` 建立整顆 NTFS 磁碟的資料夾索引，可以查詢任何資料夾的大小。
- 索引結構**和掃描方式無關**：逐目錄掃描（非 NTFS 磁碟、沒有管理員權限時的退路）要能填入同一個結構。
- 本階段**不做**：快取存檔、USN 增量更新（第 3 階段）、背景服務（第 4 階段）、前端。但資料結構要先為它們留好位置。

## 2. 實測依據（摘要）

- 需要提權。用 `GENERIC_READ` 開啟 `\\.\X:`，並啟用 `SeBackupPrivilege`。
- 回傳的 `STREAM_LAYOUT_ENTRY` 是第 1 版。大小欄位位置與 SDK 第 2 版相同，已用文件記載的 API 抽樣驗證（946 個，0 個不符）。
- 檔案資料：屬性代碼 `0x80`、識別字為空的串流。
- 與逐目錄掃描同時比對：各資料夾的檔案數、資料夾數一致；位元組差異只出現在正在寫入的檔案。
- 熱快取速度：C: 4.5 s（逐目錄 12.7 s），D: 4.6 s（逐目錄 4.1 s）。冷快取還沒量。

## 3. 資料結構

全部用連續陣列加索引，不用每個節點各自配置記憶體，也不用 `std::unordered_map`。這樣省記憶體，之後也能直接寫入快取檔。

| 表格 | 每筆內容 | 估計大小 |
|---|---|---|
| 檔案表 | 檔案 ID（64 位元）、所在資料夾索引、邏輯大小、配置大小、旗標 | 約 32 bytes |
| 額外連結表 | 只給有多個硬連結的檔案：檔案索引、另一個所在資料夾索引 | 約 8 bytes |
| 資料夾表 | 資料夾 ID（64 位元）、上層索引、第一個子資料夾、下一個兄弟、名稱位置、整棵子樹的合計（邏輯、配置、檔案數、資料夾數） | 約 64 bytes |
| 名稱池 | 所有資料夾名稱連續存放（UTF-16）。**檔案名稱不存**：檔案總管自己會顯示檔名 | 依名稱長度 |

- **為什麼要存每個檔案**：第 3 階段收到 USN 變更時，要知道檔案「原本多大」才能算出差額。比對時也看到，目錄列舉回傳的大小在檔案寫入中會落後，所以不能改用「重新列舉那個資料夾」來更新。
- **ID 用完整 64 位元**：實測用完整 ID 對應上層資料夾，孤兒為 0。不拆解 ID 內部的位元結構。
- **記憶體估計**（C: 約 110 萬檔案、20 萬資料夾）：檔案表約 35 MB，資料夾表約 13 MB，加上名稱池，合計**估計 50～60 MB**。這是估計值，實作後會量兩個數字：掃描中的峰值，以及掃描完成後的常駐記憶體。實測程式用了 557 MB，那是未經設計的版本。

## 4. 建立流程（NTFS）

1. 開啟磁碟區，用 `FSCTL_QUERY_USN_JOURNAL` 記下 `UsnJournalID` 和 `NextUsn`。**一定要在掃描開始前記**：掃描期間的變更，第 3 階段會從這個位置補上，不會漏掉。
2. 用 `FSCTL_QUERY_FILE_LAYOUT` 分批讀取，旗標：`INCLUDE_NAMES | INCLUDE_STREAMS | INCLUDE_STREAMS_WITH_NO_CLUSTERS_ALLOCATED`。
   - 每批邊讀邊轉成檔案表、資料夾表，不保留原始資料。
   - 解析器每一步都做邊界檢查。版本不認得時記錄下來，不直接中止。
3. 資料夾依 ID 排序，用二分搜尋把每個檔案的上層 ID 換成資料夾索引。
4. 由最深的資料夾往上累加，算出每個資料夾整棵子樹的合計。
5. **隱藏的系統項目**：根目錄的列舉結果中看不到的項目（中繼檔案、`$Extend` 等），整批排除並另外統計。
   - 判斷方式：用文件記載的 API 實際列出根目錄，例如 `FileIdBothDirectoryInfo`，它會回傳每個項目的檔案 ID。
   - 只依實際列出的結果判斷，不依名稱前綴，也不寫死記錄編號。

## 5. 逐目錄掃描（退路）

- 改用 `FileIdFullDirectoryInfo` 列舉，可以同時取得檔案 ID，填入同一個結構。
- 規則和 NTFS 掃描一致，所以兩種方式的結果可以直接比對。

## 6. 驗證模式

- `dirsize-cli verify X:`：同一顆磁碟用兩種方式各掃一次，逐個資料夾比對，差異會往下追查。這是從實測程式的 `--compare` 移植過來的。
- 每次修改掃描核心，都要用它確認沒有改壞。
- 解析器另外寫單元測試，用人工構造的緩衝區測截斷、offset 錯誤等異常資料。測試時開啟 MSVC AddressSanitizer。
- **已知待查**：C: 根目錄直屬檔案在兩種方式之間差約 1.63 GB。**推測**是逐目錄掃描看不到的根目錄系統檔案，尚未證實。第 4 節第 5 步完成後，用驗證模式確認。

## 7. 計算規則（已決定）

**決定（2026-11-03）**：
- **硬連結：預設採 A**，每個連結各算一次，和第 1 階段一致。檔案表仍記錄連結數，B 之後可做成選項。
- **計入範圍：以使用者在檔案總管看得到的檔案為準。** 也就是資料夾列舉回傳的項目，包含隱藏檔和系統檔（檔案總管的「內容」對話框也會計入它們）。中繼檔案、`$Extend` 和命名串流（ADS）不計入，排除的量另外統計。

### 7.1 硬連結

同一個檔案可以有多個名稱，分別放在不同資料夾（例如 Windows 系統元件）。

量測時間點 C: 的配置大小合計，與 C: 實際已用空間（476.7 GB）比較：

| 規則 | C: 合計 | 與已用空間比較 |
|---|---|---|
| A. 每個連結各算一次（第 1 階段目前的做法） | 486.5 GB | **超過**已用空間約 10 GB，代表重複計算 |
| B. 每個檔案只算一次 | 470.2 GB | 在已用空間之內 |

註：已用空間是幾分鐘後才查的，但 10 GB 的落差遠大於這段期間的檔案變動。

- **A 的優點**：每個資料夾的大小，就是裡面看得到的檔案加總，直覺；兩種掃描方式也容易保持一致。**缺點**：上層資料夾和整顆磁碟的合計會偏大，可能誤以為刪掉後能釋放更多空間。
- **B 的優點**：合計符合實際用量。**缺點**：要決定檔案算在哪一個資料夾，另一個資料夾看起來會比裡面的檔案加總少。
- 檔案表會記住每個檔案有幾個連結，所以兩種規則都能算，之後也能做成選項。

### 7.2 隱藏系統項目與命名串流

已決定**不計入**：
- 中繼檔案和 `$Extend`。其中有 1 TB 級的稀疏串流，實際上不佔空間。
- 命名串流（ADS）。

這和逐目錄掃描、檔案總管看到的一致。排除的量會另外統計，需要時可以顯示。

## 8. 速度預期

- 熱快取：C: 約快 2.8 倍；D: 和逐目錄差不多。
- 冷快取（開機後第一次）還沒量。D: 有一次 17.5 秒，可能比逐目錄慢。
- **真正的長期速度提升來自第 3 階段**：快取存檔加 USN 增量更新，開機後不用整顆重掃。第 2 階段的重點是「正確、省記憶體的完整索引」。
